Design Document · Collaborate

Authorization layer for Collaborate

Login, fine-grained permission checks at collaborative scale, and on-behalf-of delegation — built around the identity provider, not inside it.

OAuth2 OIDC RFC 8693 · Token Exchange ASP.NET Core AWS · Redis PDP

Scope. The authorization layer around an existing identity provider: OIDC-compliant login for two user populations, fine-grained permission checks at real-time collaborative scale, and on-behalf-of (OBO) delegation without a confused-deputy problem. We do not build the IdP (credentials / MFA); Caseware's central IdP and firms' own SAML/OIDC IdPs are upstream dependencies we call.

One idea underneath everything

Coarse, slow-changing authorization travels in the token and is verified locally with no network hop. Fine-grained, fast-changing authorization lives in a Policy Decision Point (PDP) cache fed by database change events. Tokens stay small and verifiable offline; revocation stays fast; the database is never on the hot path. Every decision below falls out of that split.

01 High-Level Architecture

A broker that issues, and a cache that decides

Components

  • AuthZ / Broker Service — an OAuth2 Authorization Server that brokers upstream IdPs (OIDC to the central IdP; per-firm SAML/OIDC connectors selected by client config) and mints Collaborate access + refresh tokens. Also hosts the token-exchange / OBO endpoint built in Part 2.
  • PDP cache (Redis) — per-user / per-workspace permission snapshots plus a revocation epoch. Resource APIs read it; they never touch the permissions DB directly.
  • Resource APIs — Document, Financial Data, Comments. Each validates the JWT locally (signature via cached JWKS, iss, aud, exp, scope) and consults the PDP only for the fine-grained slice.
  • Permissions DB + Projector — the source of truth. Any role/override/policy change emits an event; the projector writes the updated snapshot, bumps the principal's epoch, and publishes a revocation message.

Login — Authorization Code + PKCE

The broker pattern. Per-firm client configuration selects the upstream connector: firm staff → central Caseware IdP; external users of a federating firm → that firm's SAML/OIDC IdP, scoped to their users/workspaces. After upstream authentication Collaborate issues its own short-lived access token (~5 min) + refresh token, so downstream services trust exactly one issuer regardless of which IdP authenticated the human.

Revocation in seconds — without mass re-authentication

Three mechanisms compose:

  1. Short access-token TTL (~5 min) bounds the worst case — the floor guarantee.
  2. Revocation epoch (auth_version). Each principal has an integer epoch in Redis, embedded in every token. Any permission/membership change bumps it. Resource APIs compare the token's epoch to the current one — an O(1) read already on their PDP path; a mismatch → 401 → silent refresh, which fails closed if membership was removed. "Revoke" becomes "advance a counter."
  3. Push for long-lived connections. A collaborative editing session can outlive a refresh cycle, so the projector publishes revocations on a Redis pub/sub channel; the connection layer re-evaluates or drops affected sessions immediately. TTL is the backstop; pub/sub is the fast path.
02 On-Behalf-Of

Delegation without a confused deputy

Two delegation scenarios, one mechanism: RFC 8693 Token Exchange. A caller presents the end user's identity (subject_token) and its own (actor_token) and receives a narrower token to call one downstream as that user.

How the confused-deputy problem is defeated

  • AUD

    Mandatory audience. We require audience (RFC leaves it optional) and bind the token to exactly one downstream, so it can't be replayed against another service. The primary guard.

  • SCOPE

    Downscope to an intersection. Granted scope = requested ∩ subject-permissions ∩ actor-grant ∩ audience-allowed. Requested scope is never trusted alone; subject permissions come from the PDP, not from caller-supplied claims.

  • FIRM

    Actor scoped to firm. A client system may only act for users in its own firm; cross-firm delegation is rejected before any token is minted.

  • AUDIT

    Attribution. The token carries the RFC 8693 act.sub claim — the acting party — so the downstream call is auditable as "actor X acting as user U."

Scenario (a) client system → Collaborate as its employee and (b) internal service → downstream as the triggering user are the same exchange with different actors. Revocation uses the same epoch: minted tokens are short-lived and carry auth_version, so a bump invalidates them on the next hop without re-authenticating anyone.

03 Implementation Plan

Phased delivery

  1. Broker + issuance on the central IdP; JWT access/refresh tokens; JWKS publication + rotation.
  2. PDP + Redis + projector: DB change events → snapshots, epoch, pub/sub. Wire auth_version revocation.
  3. Resource-API authorization: shared middleware / ASP.NET Core policies for scope + fine-grained checks.
  4. Per-firm federation: SAML/OIDC connectors, per-firm client config.
  5. OBO token exchange (built in Part 2) for both delegation scenarios.
  6. Load + hardening: soak the PDP path, chaos-test Redis/IdP outages, pen-test the exchange.

AWS mapping: ALB / API Gateway → ECS/EKS services; ElastiCache (Redis) for the PDP + pub/sub; KMS for signing keys with rotation; EventBridge/outbox for DB change events; CloudWatch / OpenTelemetry for metrics and traces.

04 Testing Strategy

Prove the guards, measure the latency

  • Unit — scope downscoping (intersection math), actor-trust, epoch comparison.
  • Integration — token exchange end-to-end over the real pipeline (built in Part 2 via WebApplicationFactory), including cryptographic validation of the minted token.
  • Contract — each downstream's expected scopes/claims are pinned, so a scope rename can't silently break authz.
  • Security — the confused-deputy matrix: missing/unknown audience, scope escalation, cross-firm actor, forged/expired subject token, replay at the wrong audience.
  • Revocation latency — bump epoch → assert the next check denies; measure event→deny time.
  • Load — sustained PDP reads at target RPS; assert p99 decision latency and cache hit rate hold.
05 Evaluation & Observability

What we watch

  • Metrics — authz decision p50/p99; PDP cache hit rate; revocation propagation time (event→deny); token-exchange rate and denial reasons by OAuth error code; refresh rate; JWKS fetch errors.
  • Audit — structured log of every exchange: sub act.sub aud granted scope firm, decision. The actor chain is the audit record for OBO.
  • Tracing — one trace spanning exchange → downstream call, so a denial is attributable to a specific rule.
  • SLOs — p99 cached decision < 5 ms; revocation visible < 5 s; exchange availability ≥ 99.9%.
06 Failure Modes & Tradeoffs

Where it bends, and which way

  • Redis (PDP) outage. Fine-grained overrides fail closed — losing the source of truth for a narrowing decision must not widen access. The epoch read may fail open for a short, alarmed grace window so a blip doesn't 401 every live session; the short TTL bounds the exposure. This asymmetry is deliberate — the main safety/availability tradeoff.
  • IdP outage. JWKS is cached, so validation survives; only new logins degrade.
  • TTL vs revocation latency. Shorter TTL = faster natural revocation but more refresh load. ~5 min TTL + epoch + pub/sub gives fast revocation without very short TTLs everywhere.
  • Cache staleness vs consistency. Event-driven invalidation is the normal path; the epoch is the backstop that makes a missed event fail safe rather than fail open.
  • Downscoping complexity. Always computing an intersection is more code than honoring requested scope, but it's the only version that's safe under a confused-deputy attack.
  • JWKS rotation & clock skew. Overlapping keys during rotation; small (±30 s) skew allowance on exp/nbf.
